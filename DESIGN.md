# Sklad Ozon Design System

## Overview

### Creative North Star

Интерфейс должен ощущаться как рабочая консоль планировщика поставок: спокойная инженерная поверхность, где различия между источниками данных и решениями видны без расшифровки. Визуальный язык берётся из мира логистических схем, маршрутных ведомостей и диспетчерских панелей, но без псевдотехнического декора.

Главная визуальная подпись продукта — **линия решения**:

`Ozon → Наша потребность → План`

Пример: `72 → 104 → 96 шт.` с подписью `+32 к Ozon · +44% · +3,0 п.п. потенциала маржи`. Это единственный выраженный фирменный приём. Остальной интерфейс должен быть сдержанным и функциональным.

### Product context and register

- **Audience and primary job:** владелец/менеджер маркетплейса, который планирует FBO-поставки и должен быстро понять, где Ozon и собственная модель расходятся, сколько стоит текущая география исполнения и куда выгоднее распределить ограниченный товар.
- **Target market:** русскоязычная работа с Ozon FBO; бизнес-правила определены в `docs/superpowers/specs/2026-09-02-ozon-fbo-product-completion-design.md`.
- **Locale:** `ru-RU`. Английские технические термины допустимы только там, где они уже являются отраслевыми (`SKU`, `FBO`, `ROI`, `stockout` в диагностике). Пользовательские выводы формулируются по-русски.
- **Usage scene:** desktop/laptop, регулярная аналитическая работа с плотными таблицами и сравнением значений. Телефон не является целевой рабочей платформой, но узкие окна и 200% zoom не должны ломать доступ к функциям.
- **Register:** product/data-heavy. Маркетинговый register запрещён на рабочих экранах.
- **Memorable signature:** decision line и визуальное различение внешнего сигнала Ozon от нашей модели.
- **Restraint:** не использовать декоративные KPI-карточки, градиенты, стеклянные поверхности, большие hero-блоки, лишнюю анимацию и визуальные метафоры, не несущие данных.
- **Anti-references:** типовой SaaS dashboard с набором разноцветных карточек; глобальная Sankey/chord-«лапша»; стилизация под интерфейс Ozon; терминальные/хакерские темы; маркетинговый dark dashboard.
- **Token ownership/runtime mapping:** этот файл фиксирует утверждённые системные решения. На момент создания текущий `frontend/assets/css/app.css` является legacy-реализацией и не соответствует этому контракту. В Product Completion implementation значения должны быть сопоставлены один-к-одному с CSS custom properties в едином глобальном token block; screen-local копирование hex/radius/spacing запрещено. После миграции runtime CSS становится исполняемым владельцем, а `DESIGN.md` обязан зеркалить его без расхождений.

## Colors

Фон приложения — `canvas`. Все рабочие панели — `surface`; `surface-muted` используется для вторичной аналитики, итоговых строк и нейтральных выбранных областей. Основной текст — `text`, вторичный — `text-muted`, разделители — `border`.

Семантика цвета обязательна:

- `ozon` — только внешний сигнал Ozon: исходная рекомендация, Ozon horizon, Ozon-side reference. Не использовать как универсальный primary-action цвет.
- `model` — собственная модель, расчётная потребность, рассчитанный план и основное безопасное действие.
- `warning` — экономическая переплата, вероятное искажение, неполная сопоставимость горизонтов и другие состояния, требующие внимания, но не означающие ошибку.
- `success` — подтверждённое положительное/полное состояние: корректно загруженные данные, локальное исполнение без существенной переплаты, полный расчёт.
- `danger` — только ошибки, физическая невозможность, критически неполные данные и блокирующие состояния.
- `focus` — единый видимый focus ring.

Расхождение с Ozon не является ошибкой и не окрашивается красным.

Цвет никогда не является единственным носителем статуса: рядом всегда есть текст, знак, направление стрелки или подпись.

## Typography

Основной интерфейсный шрифт — `Golos Text` с системными fallback. Числовой/технический слой — `JetBrains Mono` для SKU, процентов, денежных значений в цепочках сравнения, динамики `19,5 → 24,5 → 29` и диагностических кодов.

Шрифты должны быть локальными/закоммиченными или иметь гарантированный offline fallback. Runtime CDN запрещён. Если выбранные webfont assets не могут быть надёжно поставлены в проект, реализация должна использовать fallback stack без сетевого запроса и зафиксировать отклонение, а не подключать внешний CDN.

Заголовки спокойные, без display-типографики. Иерархия создаётся размером, весом и пространством. В таблицах и аналитических блоках приоритет — числовая выравниваемость и быстрое сравнение.

Все проценты маршрута форматируются как `%`, изменения маржи — как `п.п.`, деньги — `ru-RU` с `₽`, количество — `шт.` там, где единица не очевидна из заголовка.

## Layout

Основной desktop shell использует доступную ширину до `page-max`. Планировщик — это плотный инструмент; чрезмерные пустые поля недопустимы.

Основные маршруты приложения:

1. **План** — decision table и итоговый план поставки.
2. **Потоки спроса** — визуальная география destination/origin/SKU.
3. **Экономика** — детальная юнитка и маршрутные затраты.
4. **Данные** — импорт, актуальность, настройки и mappings.

Главный экран «План» строится сверху вниз: контекст данных → сценарий → decision line → фильтры → таблица. Детали строки открываются в широком правом drawer, а не в модальном окне.

«Потоки спроса» имеют трёхзонную desktop-композицию:

- слева — список/карточки кластеров;
- центр — hub-and-spoke выбранного кластера или SKU-oriented flow view;
- справа — контекст выбранного узла/маршрута;
- ниже — ранжированный SKU breakdown выбранной связи.

Главная flow-визуализация всегда фокусируется на одном destination/origin/SKU. Глобальная Sankey/chord диаграмма по всем кластерам не используется как основной экран.

Таблица является отдельным scroll-owner. Header и toolbar остаются видимыми; строки прокручиваются внутри bounded table surface. На узких окнах сохраняется горизонтальная прокрутка связанной таблицы, а вторичные колонки могут быть скрыты только через явный column chooser.

## Elevation & Depth

Иерархия в основном строится фоном, границей и spacing. Статические карточки не получают тяжёлые тени. Drawer и popover могут использовать небольшую тень только для отделения от underlying content. Sticky header/table toolbar должны иметь непрозрачный surface background.

Не использовать blur/glassmorphism.

## Shapes

Стандартный radius — `md`. Controls и небольшие аналитические блоки используют `sm`/`md`; крупный drawer и крупные surface-группы — `lg`. Pill разрешён только для компактных фильтров/status badges, а не для всех кнопок.

Толстые декоративные рамки запрещены. Акцентные линии должны кодировать данные или активное состояние.

## Components

### Foundational visual states

Каждый интерактивный компонент имеет default, hover, focus-visible, active, disabled и busy состояния без изменения геометрии. Выбранное состояние обозначается не только цветом. Error и warning визуально различаются. Loading оставляет стабильную геометрию.

### Buttons and actions

Основное действие в decision area использует `model`. Neutral действия — outline/ghost. Danger используется только для блокирующих/разрушающих действий, которых в текущем read-oriented продукте почти нет.

Текст кнопки описывает действие: `Пересчитать план`, `Очистить фильтры`, `Открыть детали`, `Применить сопоставление`.

### Navigation and data display

Главная навигация компактная и постоянная на desktop. Активный раздел имеет текстовый и визуальный признак.

Decision table сохраняет идентификатор товара и кластер визуально стабильными при горизонтальной прокрутке, если это не создаёт конфликтов при zoom/focus.

Decision line — отдельный системный компонент, использующий семантику `ozon` для первого значения и `model` для собственной оценки/плана.

Cluster cards в «Потоках спроса» показывают общий спрос, локальный %, внешний %, число доноров и экономический эффект. Они не должны превращаться в KPI-card mosaic: все карточки имеют одну структуру и предназначены для сравнения.

Flow diagram:

- центральный узел — выбранный destination/origin;
- толщина связи кодирует активную метрику;
- локальная связь визуально нейтрально-положительная;
- внешние связи используют warning-семантику по мере экономической нагрузки;
- каждая связь имеет доступный текстовый эквивалент и может быть выбрана клавиатурой;
- ширина/цвет не являются единственными источниками численного значения.

SKU breakdown выбранного маршрута — ранжированные горизонтальные bars с точными значениями рядом: SKU/article, штуки, доля маршрута, доля destination-demand и экономический эффект.

### Forms and overlays

Форма импорта живёт в разделе «Данные», а не на главном decision screen. Нативный `input[type=file]` допустим как underlying control, но UI обязан показывать выбранный файл, состояние проверки и ошибку рядом.

Detail drawer — немодальный persistent contextual surface: не блокирует основной список, не ставит inert background и не использует focus trap. При открытии focus переводится на заголовок/первое релевантное действие, при закрытии возвращается на исходную строку.

### Iconography

Использовать простые inline SVG-иконки одного stroke-стиля. Иконка не заменяет подпись у бизнес-действий. Не использовать emoji как системные иконки.

### Motion

Motion минимален и сообщает состояние: открытие drawer, изменение selected node, прогресс расчёта. Обычная длительность 120–180 ms. Data values не должны «вылетать» или анимироваться ради эффекта. `prefers-reduced-motion` убирает необязательные переходы.

### Content and data visualization

Интерфейс говорит от стороны пользователя: `Ozon рекомендует`, `Наша потребность`, `План`, `Вероятный дефицит`, `Рекомендация может быть искажена`, `Маршрут дороже локального на 3,0 п.п.`.

В product surfaces не выводятся сырые backend codes вместо пользовательского текста. Codes доступны только в диагностическом disclosure.

Графические представления всегда имеют числовой текстовый эквивалент. Tooltip дополняет, но не является единственным способом узнать значение.

## Do's and Don'ts

- **Do:** делать различие `Ozon → Наша модель → План` очевидным в каждом месте, где пользователь принимает решение.
- **Do:** показывать маршрут одновременно в штуках, доле и экономическом эффекте, когда это влияет на решение.
- **Do:** давать пользователю возможность перейти от сводки к доказательству без технических кодов на основном пути.
- **Do:** держать визуальный язык плотным, спокойным и сравнимым между экранами.
- **Don't:** превращать экран в набор декоративных KPI-карточек.
- **Don't:** использовать красный для обычного несогласия с Ozon.
- **Don't:** использовать глобальный Sankey/chord как главный способ анализа всех кластеров.
- **Don't:** прятать точное значение только в hover/tooltip или кодировать смысл только цветом.
