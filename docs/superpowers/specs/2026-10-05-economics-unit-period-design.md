# ТЗ: юнитка SKU и единая прибыль за период

Проект: `vgvolmax/sklad_ozon`, вкладка «Экономика». Дата: 05.10.2026.

Основание проверки: ветка `codex/economics-buyouts-expenses`, коммит `e8c030a`, открытый PR №206. Документ описывает следующий объём доработки, а не уже реализованное поведение. Реализация — в отдельном PR после проверки актуальной базы; слияние и автоматическое слияние не выполнять.

## 1. Результат для пользователя

На вкладке решаются две самостоятельные задачи:

1. **Юнитка SKU:** оценить прибыльность одной штуки при текущей цене и определить цену для выбранной цели. Работает и без продаж.
2. **Прибыль за период:** умножить прибыль на штуку из той же юнитки на количество заказов либо выкупов, затем вычесть одинаковые общие расходы выбранного периода.

«По заказам / По выкупам» находится внутри итоговой панели. Переключатель не заменяет вкладку, не меняет юнитку, целевые цены или графики SKU.

Это управленческая модель по текущей себестоимости, ценам и известным расходам. Совпадение с выплатой Ozon или бухгалтерским результатом до копейки не является целью.

## 2. Что согласовано и какие решения приняты в ТЗ

### Подтверждённые требования

- Одинаковая прибыль на штуку используется в обоих режимах итоговой панели.
- Отличается только количество: заказы либо выкупленные штуки.
- Общая реклама берётся суммой в рублях за период; распределение между SKU для общего итога не требуется.
- Прочие расходы периода нужны в обоих режимах и учитываются один раз.
- Себестоимость актуальна на момент загрузки. Новая история себестоимости по месяцам не нужна.
- SKU без продаж должен получать расчёт цены; графики, СПП и клиентская цена ему не требуются.
- Нужна настройка подстановки планового ДРР при отсутствии реального рекламного отчёта.
- Существующие карточки с историей, фильтры, копирование SKU, графики и выгрузки сохраняются.

### Проектные допущения, которые нужно сверить при ревью ТЗ

Эти решения устраняют неоднозначности, но не выдаются за отдельные указания пользователя:

| Вопрос | Решение в этом ТЗ |
|---|---|
| Что считать заказами | Все заказанные штуки FBO/FBS с известными статусами «в работе» и «доставлен», по дате принятия; отменённые исключены. Это шире нынешнего расчёта только по доставленным. |
| Дата выкупа | Дата финансового начисления реализации, возврат — по дате обратного начисления. Не называть это датой покупки клиентом. |
| Источник общих расходов | Единый финансовый реестр Ozon за выбранные даты. Рекламные XLSX продолжают обслуживать ДРР SKU и повторно к общим расходам не прибавляются. |
| Подстановка ДРР по плану по умолчанию | Выключена, чтобы обновление не изменяло сохранённые расчёты без явного выбора. При включении работает для всех SKU с отсутствующим отчётом, с учётом индивидуального планового ДРР. |
| SKU без собственной истории маршрутов | Пользователь выбирает доступный источник отгрузки и направления. Для нескольких направлений расчёт консервативный, по самому дорогому известному варианту. |
| Выбранный период | Один существующий календарный период «Экономики» для карточек и панели. Переключение режима панели этот период не меняет. |

Если при ревью меняется одно из этих решений, сначала корректируются его формулы и приёмочные сценарии. Не менять определения скрыто во время реализации.

## 3. Границы изменения

### Входит

- Расчёт и отдельное представление SKU без продаж.
- Подстановка планового ДРР с сохранением происхождения значения.
- Пересчёт подходящего тарифа при подборе целевой цены.
- Единая прибыль на штуку до рекламы для итоговой панели.
- Независимая загрузка количеств и общих расходов за период.
- Локальный переключатель «По заказам / По выкупам».
- Обновление XLSX, ошибок, состояний загрузки, документации и проверок.

### Сохраняется

- Каноническая идентичность — SKU. Одинаковый артикул не объединяет разные SKU.
- В API-режиме список активных карточек определяется каталогом Ozon, включая новые товары с нулевыми остатками и без продаж.
- Правила источников API/FILES, текущие приоритеты валидных API-фактов и явно обозначенных данных юнитки.
- Математика спроса, потребности, распределения поставок, «План» и «Потоки спроса».
- Средневзвешенные СПП и клиентские цены, дневные/недельные графики для SKU с историей.
- Поддерживаемый portable Windows runtime: Python/FastAPI, committed vanilla HTML/CSS/JS. Новые фреймворки, БД и фоновые службы не добавляются.

Из финансовых данных больше не вычислять прибыль итоговой панели как «чистые начисления минус себестоимость». Финансовые данные дают количества выкупов/возвратов и расходы; прибыль на штуку даёт юнитка.

## 4. Исходные данные и их владельцы

| Данные | Владелец / источник | Правило отсутствия |
|---|---|---|
| SKU, артикул, название | Текущий каталог Ozon, нормализованная идентичность | Неразрешённую идентичность не объединять по названию или артикулу. |
| Себестоимость | Последний загруженный файл, сопоставление по SKU | Не подменять нулём или историческим значением. Для текущего расчёта загрузка имеет приоритет над ранее сохранённой себестоимостью. |
| Текущая цена продавца | Текущие нормализованные факты; в FILES — соответствующий источник | Можно подобрать целевую цену без текущей, но нельзя показать текущую прибыль и изменение цены. |
| Комиссия | Известная ставка SKU | Не выводить её из продаж, если ставки нет. Неизвестная ставка блокирует полную цену. |

| Тарифы | Загруженная нормализованная таблица `TariffRow` | Пропуск или несколько совпадений — неполный расчёт, не бесплатная логистика. |
| Налоги, эквайринг, выкупность, фиксированная FBO-плата | Существующие `EconomicsSettings` | Сохранить текущие поддерживаемые формулы и ограничения. |
| Плановый ДРР | Общая настройка, затем индивидуальное значение SKU | Индивидуальное значение, включая 0%, имеет приоритет. |
| Реальный ДРР SKU | Рекламные XLSX + стоимость всех заказов за соответствующие дни | Отсутствие отчёта и невозможность расчёта по имеющемуся отчёту — разные состояния. |
| Количество заказанных штук | Датированные нормализованные заказы | Неизвестная история — не 0. |
| Количество выкупленных/возвращённых штук | Финансовые события реализации/возврата | Частичный возврат нельзя восстанавливать полным количеством исходного отправления. |
| Общие расходы | Финансовые начисления за период | Неизвестный/незагруженный период — не 0. |

Новый механизм не сохраняет помесячные себестоимости. Существующий справочник и ручные правки не удаляются, но не должны переопределять новую загрузку при расчёте этой модели. Чисто расчётные маршруты SKU хранятся в текущем состоянии «Экономики», по SKU и снимку; новый долговременный справочник для них не требуется.

## 5. Единая юнитка

### 5.1. Два результата на одну штуку

Для каждого SKU сервер возвращает:

- `profit_per_unit_before_ads` — прибыль на штуку без рекламного расхода; используется только как база итоговой панели.
- Прибыль/маржу/ROI при текущей цене с применённым ДРР — отображаемый сценарий карточки SKU.

Оба результата используют одинаковые исходные цену, себестоимость, маршруты, комиссию, налоги и прочие параметры. Различается только рекламная составляющая. «До рекламы» нужно заново вычислять с ДРР=0 через каноническую формулу, а не просто прибавлять рекламные рубли к прибыли: при УСН «доходы минус расходы» меняется налоговая база.

Расчёты выполняются на backend с `Decimal`. Frontend форматирует значения и управляет состоянием, но не дублирует финансовые формулы.

### 5.2. Как получается одно значение при нескольких маршрутах

- Для SKU с собственной историей использовать существующее взвешивание маршрутов по количеству доставленных штук в выбранном периоде. Веса фиксируются при построении базы и одинаковы для обоих режимов панели.
- Если в выбранном периоде нет доставленных маршрутов, но они есть в загруженной истории, разрешён явно обозначенный расчёт по этой истории. Даты и источник весов возвращаются сервером.
- Если собственной истории нет, использовать выбранные пользователем расчётные маршруты. Для нескольких направлений текущая расчётная прибыль берётся минимальной из полностью известных маршрутов; целевая цена — максимальной из требуемых цен. Подпись: «Расчёт по самому дорогому выбранному маршруту».
- Не пересчитывать веса по выкупам при переключении панели. Иначе изменятся одновременно количество и база, что нарушает согласованную модель.
- Неполные маршруты не переименовывать в полный расчёт. Известную часть показывать отдельно с покрытием; итог не считать полным.

Требование одинаковой базы проверяется сравнением версии/отпечатка расчётных входов в двух режимах панели.

### 5.3. Учитываемые расходы на единицу

Повторно использовать существующий калькулятор `calculate_unit_economics`: себестоимость, комиссия, эквайринг, доставка, фиксированная FBO-плата, заложенная модель обратной логистики/выкупности, поддерживаемые налоги и соинвестирование.

Для проверки логистической части сохраняется действующая формула:

`L = (T + F) / B + (1 / B − 1) × T`,

где `T` — тариф доставки по объёму, цене и маршруту; `F` — фиксированная FBO-плата; `B` — заданная выкупность (0 < B ≤ 1).

При переключении количества заказов на количество выкупов не вводить второй коэффициент выкупности и не умножать его повторно. Это сравнение одной модели на двух количествах, а не точная реконструкция затрат по каждому статусу.

Общие расходы после суммирования не изменяют заново модельный налог на единицу. Это ограничение управленческой модели явно указать в раскрытии методики; отдельную бухгалтерскую налоговую модель в этот PR не добавлять.

## 6. Плановый ДРР при отсутствии отчёта

Добавить в существующий блок целей переключатель:

**«Использовать плановый ДРР, если нет рекламного отчёта»**.

Его значение сохраняется рядом с текущими настройками «Экономики». При чтении старых настроек отсутствующее поле означает `false`.

| Состояние | Применённый ДРР карточки | Отображение |
|---|---|---|
| Реальный ДРР рассчитан и >0 | Реальный | «Реальный 8% · В расчёте 8%». |
| Реальный ДРР рассчитан и =0 | 0%, независимо от переключателя | «Реальный 0%». |
| Для SKU нет отчёта за выбранные даты, переключатель включён | Индивидуальный плановый либо общий | «Реальный n/a · В расчёте 15% из плана». |
| Нет отчёта, переключатель выключен | 0% | «Реальный n/a · В расчёте 0%, допущение». |
| Отчёт есть, но нет полной истории/цен/положительного знаменателя | Значение не определено | Причина и неполный результат; не маскировать повреждённую доказательную базу под отсутствие отчёта. |

Хранить раздельно реальный, плановый и применённый ДРР и источник подстановки. Не записывать плановый процент в поле «реальный». Недостаточно проверять значение через `value || fallback`: реальный и индивидуальный плановый ноль валидны.

Переключатель влияет на сценарий текущей цены карточки, её маржу, ROI, недобор и соответствующие фильтры. Целевая цена по-прежнему использует плановый ДРР. База итоговой панели до рекламы от этой настройки не меняется.

Загруженный отчёт, покрывающий только часть выбранного периода, сохраняет текущую методику ДРР по известным дням с явными датами покрытия. Не утверждать, что это фактический расход всех дней выбранного периода.

## 7. SKU без продаж

### 7.1. Условие отдельного представления

Вариант «Расчёт без продаж» используется при отсутствии собственной истории доставленных продаж во всём загруженном наблюдении. Наличие заказов в пути показывать отдельным счётчиком, если они есть.

Не считать SKU новым только потому, что в выбранном коротком периоде нет продаж. Для него сохраняются доступные исторические данные и обычное представление с честным пустым периодом. Отсутствие истории и ошибка её загрузки — разные состояния.

### 7.2. Состав компактной карточки

- Артикул, название, SKU и существующая иконка копирования.
- Текущая цена продавца и себестоимость из загрузки.
- Объём единицы, комиссия в процентах и рублях при текущей цене.
- Плановый ДРР, применённый ДРР и происхождение значения.
- Выбор источника отгрузки и одного либо нескольких направлений из известной тарифной матрицы.
- Раскрытие «Расходы на штуку»: комиссия, эквайринг, логистика, прочие модельные строки, налоги, реклама сценария.
- Прибыль, маржа и ROI при текущей цене с подписью «Расчёт».
- Целевая цена продавца, выбранная цель и ограничивающий маршрут.
- Разница между текущей и целевой ценой, если текущая известна.

Не показывать пустые графики, СПП, клиентские цены и колонку доставленных продаж как обязательные части этого варианта. Нулевая история не является ошибкой расчёта.

При одном подходящем источнике его можно выбрать автоматически, отобразив название. При нескольких пользователь выбирает источник. Направления явно выбраны пользователем, неизвестное распределение спроса не выдумывается. В состоянии без выбранных маршрутов показывать конкретное действие «Выберите маршруты для расчёта».

Выбор маршрутов применяется только к юнитке и базе итоговой панели. Он не создаёт планы поставок, не меняет спрос или потребность и не вызывает внешние операции.

### 7.3. Частичные входы

- Известны себестоимость и необходимые ставки/маршруты, текущей цены нет: подобрать целевую; текущая прибыль, клиентская цена и изменение цены остаются неизвестными.
- Нет себестоимости/комиссии/объёма/тарифа: назвать недостающие поля и сохранить остальные введённые значения.
- Себестоимость 0 валидна для цели по марже; ROI при нулевой себестоимости не определён. Для цели по ROI объяснить невозможность расчёта.
- Пустая строка себестоимости не означает 0.
- Если по отдельному маршруту цель недостижима, единую цену не выдавать как достаточную.

## 8. Целевая цена и сравнение плана с текущим расчётом

Цель выбирается существующим переключателем: маржа либо ROI. Второе поле остаётся ориентиром, но не становится скрытым дополнительным ограничением.

Для каждого выбранного/известного маршрута найти минимальную положительную цену с шагом 0,01 ₽, обеспечивающую выбранную цель при плановом ДРР. Единая цена SKU — максимум требуемых цен по маршрутам при полном покрытии.

При каждой проверяемой цене заново подобрать тариф по объёму, маршруту и ценовому диапазону. Для ступенчатых тарифов нельзя полагаться на монотонность общей функции через границу: искать допустимую цену по отдельным диапазонам, проверять границы и выбирать минимальную подходящую. Ставку комиссии считать фиксированной известной ставкой SKU, пока нормализованный источник не предоставляет отдельной зависимости от цены.

Рядом с предложенной ценой показать:

- выбранную цель;
- плановый ДРР;
- ограничивающий маршрут;
- при необходимости предупреждение о неполных тарифах/исходных данных.

Если предложенная цена ниже текущей, сохранить существующее выделение и текст «Можно снизить». Если выше — показать сумму и процент повышения. Равенство означает «Цена соответствует цели».

Для карточек с историей текущий расчёт и план остаются в двух строках. При подстановке планового ДРР прибыль нельзя подписывать как безусловный «Факт»: использовать «Расчёт при текущей цене» и явное происхождение ДРР. Существующие цвета факта и плана сохраняются; одна только окраска не заменяет подпись.

## 9. Итоговая панель «Прибыль за период»

### 9.1. Формулы

Для каждого SKU `s`:

- `u[s]` — прибыль на штуку до рекламы из единой базы юнитки;
- `q_orders[s]` — заказанные штуки за выбранные даты;
- `q_buyouts[s]` — выкупленные штуки минус возвращённые за выбранные даты.

`profit_before_common(mode) = Σ(u[s] × q_mode[s])`.

`profit_after_common(mode) = profit_before_common(mode) − advertising_total − other_common_total`.

`advertising_total` и `other_common_total` одинаковы при одном кабинете, периоде и версии реестра расходов независимо от режима.

Модельная выручка для маржи: `revenue_model(mode) = Σ(current_seller_price[s] × q_mode[s])`.

Маржа после общих расходов: `profit_after_common / revenue_model`, только если знаменатель >0 и сопоставимое покрытие известно. Фактическую клиентскую цену и суммы выплат в этот знаменатель не подставлять. Неполный процент явно обозначать как расчёт по известной части либо не показывать полную маржу.

### 9.2. Пример для приёмки

| SKU | Прибыль на штуку до рекламы | Заказано | Выкуплено с учётом возвратов |
|---|---:|---:|---:|
| A | 150 ₽ | 100 шт. | 70 шт. |
| B | 80 ₽ | 50 шт. | 30 шт. |

Реклама за период — 5 000 ₽, остальные общие расходы — 2 000 ₽.

- По заказам: `150×100 + 80×50 = 19 000 ₽`; итог `19 000 − 5 000 − 2 000 = 12 000 ₽`.
- По выкупам: `150×70 + 80×30 = 12 900 ₽`; итог `12 900 − 5 000 − 2 000 = 5 900 ₽`.
- При переключении реклама остаётся 5 000 ₽, прочие расходы 2 000 ₽, база на штуку 150/80 ₽.
- Изменение планового ДРР при неизменных прочих входах не изменяет этот итог. Подстановка ДРР изменяет карточки SKU, но не второй раз вычитает рекламу в панели.

### 9.3. Количества и даты

Для заказов считать штуки, а не число отправлений. Один заказ с двумя SKU или тремя штуками правильно раскладывается по SKU. Включать `IN_PROGRESS` и `FULFILLED`, исключать `CANCELLED`; неизвестные статусы показывать в диагностике. Отсутствующий склад отгрузки не исключает сам заказ из количества: для юнитки используется заранее определённая расчётная база.

Состав заказов панели не менять в канонической математике Demand/Plan/Flow и не переносить автоматически на графики или знаменатель ДРР: у этих показателей уже есть свои определения.

Для выкупов учитывать подписанные количественные события реализации/возврата, а не число положительных финансовых строк. Услуга/комиссия/корректировка без реализации имеет количество 0 и не увеличивает выкупы. Повторные страницы и события не удваивают количество. Частичный возврат уменьшает количество только на известные возвращённые штуки.

Возврат товара, проданного раньше выбранного периода, уменьшает количество текущего периода по дате возврата. Отрицательное итоговое количество допустимо; не обрезать до 0. Маржа с неположительной модельной выручкой не рассчитывается.

Период включительный, бизнес-время UTC+03:00. Один календарный диапазон может содержать разные события: принятые в нём заказы и начисленные в нём выкупы не являются одной когортой. Не показывать их отношение как выкупность периода.

### 9.4. Состав панели

- Заголовок «Прибыль за период», даты, подпись «Весь магазин · модель по текущей юнитке».
- Локальный переключатель «По заказам / По выкупам».
- Количество штук и, для выкупов, отдельные счётчики выкуплено/возвращено.
- Модельная выручка, прибыль по товарам до общих расходов.
- Отдельная строка «Реклама за период».
- Отдельная строка «Прочие общие расходы».
- Итог «Прибыль после известных расходов» и маржа при полном покрытии.
- Дата/время загрузки расходов и их источник.
- Раскрытие категорий общих расходов и перечня исключённых/неопределённых строк.
- Покрытие: сколько штук/SKU имеют полную юнитку и какие данные не загружены.
- Кнопка загрузки/обновления количеств выкупов и расходов, прогресс, отмена и повтор при ошибке.

Суммы расходов принадлежат панели и загружаются независимо от того, какой режим количества выбран. В режиме заказов загрузка общих расходов также доступна.

### 9.5. Общий итог и фильтры

Основной итог охватывает весь магазин, включая рекламу SKU, у которых нет заказов в выбранном периоде. Расход не исчезает из-за отсутствия продаж товара.

Поиск/фильтры списка SKU не урезают общие расходы магазина и не меняют основной итог. При активном фильтре показывать дополнительную строку «Прибыль выбранных SKU до общих расходов»; не называть её окончательной прибылью выбранных товаров.

Старые SKU, присутствующие в выкупах, но отсутствующие в текущем каталоге, входят в общий расчёт, если для них есть явные актуальные входы юнитки. Их не возвращать в активный ассортимент Plan. Без полной юнитки соответствующее количество отмечается как непокрытое.

## 10. Общие расходы и защита от двойного учёта

### 10.1. Реклама

Суммировать все известные рекламные расходы магазина за выбранные даты, независимо от привязки к SKU. Использовать один источник, период, валюту и версию данных для обоих режимов. Не вычислять общий расход умножением среднего/планового ДРР на выручку.

Рекламные файлы, загруженные для ДРР карточек, не прибавляются к рекламе из финансовых начислений. Источник расхода панели — финансовый реестр. Если реестр не загружен, известные расходы отдельных XLSX не выдаются за полный расход магазина; показать отсутствие финансового источника и сохранить рассчитанную прибыль до общих расходов.

Рекламное начисление с SKU всё равно входит в общий рекламный расход. Его принадлежность SKU не означает, что реклама уже вычтена из базы `profit_per_unit_before_ads`.

### 10.2. Другие категории

На backend каждой строке назначается одна из ролей:

| Роль | Пример | Участие в окончательном итоге |
|---|---|---|
| `advertising` | Любая известная рекламная услуга | Вычесть в рекламе один раз. |
| `additional_period_expense` | Известное хранение, кросс-докинг, приёмка, услуга/штраф, не включённые в юнитку | Вычесть в прочих расходах один раз. |
| `already_in_unit_model` | Комиссия, эквайринг, доставка/обратная логистика в пределах действующей модели | Показать в расшифровке как уже учтённые; второй раз не вычитать. |
| `not_an_expense` | Выручка реализации, выплата, ценовая компенсация | Не превращать в общий расход. |
| `unclassified` | Неизвестный тип начисления или спорная корректировка | Показать сумму и описание отдельно; не считать итог полным. |

Классификация зависит от вида услуги и состава юнитки, а не только от наличия SKU. Хранение с привязкой к SKU может быть дополнительным расходом; доставка без SKU может дублировать уже учтённую модель.

Не использовать «выручка минус выплата» как общие расходы: в разнице уже содержатся части юнитки. Не суммировать одновременно общий итог начисления и его вложенные строки. Неизвестный остаток не скрывать под произвольной категорией.

Возвраты услуг/корректировки учитываются со знаком: отрицательный расход уменьшает соответствующую категорию. Валюту и налоговую базу сумм сохранять из нормализованного источника; повторно начислять НДС поверх уже переданной суммы нельзя.

### 10.3. Нет данных и частичная загрузка

- Полная успешная загрузка, расходов нет: известный 0.
- Расходы не загружены либо загрузка покрывает не все даты: неизвестно, не 0.
- Известна реклама, часть других строк не классифицирована: показать результат по известным расходам и признак неполноты.
- Нет юнитки для части количества: показывать известную часть прибыли и покрытие. Вычитание общих расходов из известной части допустимо только с подписью «Известная часть результата».
- Неуспешное обновление не заменяет предыдущие полные данные пустым набором. Сохраняется прежний период с явной ошибкой; нельзя показывать его как новый выбранный диапазон.

## 11. Поведение интерфейса и состояния

Переключение режима выполняется внутри панели. Внешний контейнер карточек SKU не перерисовывается. Сохраняются поиск, фильтр, раскрытый артикул/кластер, внутренний скролл кластеров, положение страницы, несохранённые поля и графики.

Если данные количества уже загружены, переключение меняет итог сразу. Если выкупы ещё не загружены, панель предлагает загрузку; карточки остаются доступны. Запрос расходов не запускать повторно только из-за смены режима при том же кабинете/периоде.

Существующее изменение периода может обновлять средние, ДРР и карточки согласно их методике. Оно отличается от смены режима количества и не должно вызываться этим переключателем.

Предусмотреть состояния панели: начальное, загрузка, полный результат, частичный результат, пустой период, ошибка, отмена, устаревший результат. В каждом случае даты и источник видимы. Для пустого периода с известными общими расходами итог может быть отрицательным: расходы не исчезают из-за нулевого количества.

Старый ответ не перезаписывает новый период, снимок, настройки или кабинет. Неверные/пустые даты не отправляются. Период заказов ограничен загруженной историей, финансовые даты — существующими валидаторами. Данные разных кабинетов не смешиваются.

Нативные семантические элементы, русские подписи, фокус клавиатуры, `aria-pressed` у сегментов, доступные статусы и ошибки. Узкая ширина и 200% масштаб не создают горизонтального скролла всей страницы; широкие таблицы скроллятся внутри. Успех копирования SKU показывается существующим маленьким попапом, без отдельной подсказки.

## 12. XLSX

Существующий экспорт карточек выгружает все позиции, прошедшие фильтр, а не только видимые 12 строк. Сохранить старые поля и добавить без изменения их смысла:

- тип карточки: с историей / расчёт без продаж;
- реальный, плановый и применённый ДРР, источник применённого значения;
- прибыль на штуку до рекламы;
- основание расчёта маршрутов, ограничивающий маршрут и признаки неполноты.

Экспорт итоговой панели содержит листы:

1. «Итог»: кабинет без секретов, выбранные даты, режим количества, полный итог магазина, общие расходы, источник, версия базы и покрытие.
2. «Товары»: SKU/артикул/название, прибыль на штуку до рекламы, количество выбранного режима, вклад в прибыль, текущая цена, модельная выручка и статус входов. Применяется текущий фильтр; на листе указано, что это выборка.
3. «Расходы»: весь магазин, категории, суммы со знаком, роль строки и причина исключения/неполноты. Распределять рекламу по SKU не требуется.

Если основной итог не зависит от фильтра, это явно подписано на листе «Итог». Не выдавать сумму отфильтрованных строк за итог магазина. Выгрузка использует те же backend-значения, что экран. Пользовательский текст записывается безопасно как текст; строки не превращаются в Excel-формулы.

## 14. Техническое приложение

### 14.1. Вердикт — REFACTOR-IN-PR

Нужно ограниченное разделение владельцев состояния и расчётных входов внутри «Экономики», вместе с новой функциональностью. Отдельная переработка всего приложения не требуется.

Основания в текущем коде:

- `frontend/assets/js/economics_workspace.js`: `draw()` в режиме buyouts передаёт весь контейнер `EconomicsBuyouts.render()`; это напрямую заменяет вкладку.
- `backend/economics/workspace.py`: сумма/цель строится из маршрутов с положительным количеством. SKU без маршрутов виден, но целевая цена отсутствует. `rates.get(sku) or ZERO` задаёт нынешнее допущение для n/a.
- `backend/economics/buyouts.py`: прибыль сейчас выводится из `net_amount − cost_total`; это другая база, чем согласованная юнитка.
- `backend/economics/summary.py`: расходы рекламы берутся из выбранных товаров, а не полного реестра магазина.
- `backend/economics/tariffs.py` и `unit.py` уже содержат независимые тарифный и единичный калькуляторы; `TariffRow` имеет ценовые диапазоны.
- `AnalysisSnapshot` хранит результаты маршрутов, но не полную независимую базу для нового подбора цен. `buyout_cost_inputs` — текущие входы себестоимости до сохранённых правок, а не готовая база всех ставок/тарифов.

Без этого разделения режим количества продолжит заменять UI, а расчёт без продаж потребует искусственных продаж либо дублей формул. Подготовка ограничена перечисленными владельцами и проверяется сохранением поведения до новых изменений.

### 14.2. Влияние изменения

| Область | Изменение | Инвариант |
|---|---|---|
| `backend/decision/contracts.py`, сборка снимка в `backend/api.py` | Backend-only неизменяемые входы цены/ставок/объёма/тарифов и количества по датам | Не добавлять приватные финансовые/сырьевые данные в wire/Project JSON. |
| `backend/economics/unit.py`, `tariffs.py`, `workspace.py` | Единичная база до рекламы, подбор тарифа при новой цене, происхождение ДРР | Одна каноническая формула, нет зависимости от выбранного режима панели. |
| `backend/economics/summary.py`, `buyouts.py`, `buyout_api.py` | Количественные события и единый итог с общими расходами | Не использовать чистые выплаты как прибыль товара. |
| `backend/ozon/adapters/finance.py` | Явные роли расходов и количественные события/покрытие | Пагинация, дедупликация, знаки, атомарность, PII-safe нормализация. |
| `frontend/assets/js/economics_workspace.js`, `economics_buyouts.js` | SKU-workspace постоянно смонтирован, финансовый владелец получает только панель | Без замены внешнего контейнера и без потери редактирования. |
| `backend/economics/export.py` | Экспорт единой модели/источников/покрытия | Те же расчёты, что на экране; фильтр не меняет расходы магазина. |
| Корневые UI-контракты и приёмка | Обновить текущие правила режима buyouts и n/a | Новое согласованное ТЗ намеренно заменяет противоречащие старые правила. |

### 14.3. Технический дизайн

Минимальные фокусные владельцы:

1. **Входы и база юнитки.** При успешной загрузке/анализе собрать неизменяемый набор фактов SKU и тарифов, достаточный для расчёта без истории. Чистый публичный вход калькулятора принимает эти факты, настройки, цели и расчётные маршруты. Результат содержит обе прибыли на штуку, статус входов, покрытие и источник маршрутов. Допустимо добавить один модуль `backend/economics/pricing.py` для подбора цены, если изменение нельзя ясно разместить в текущих владельцах; повторной формулы прибыли не создавать.
2. **Количество периода.** Отдельный агрегатор возвращает по SKU заказанные штуки и подписанные выкупы/возвраты, их основания дат и полноту. Он не вычисляет прибыль.
3. **Реестр расходов.** Нормализатор возвращает подписанные суммы с датой, типом услуги, ролью относительно модели и покрытием периода. Связь с SKU необязательна. Стабильный идентификатор записи допускается в backend для дедупликации; сырые отправления/PII не сохраняются.
4. **Итог.** Чистый агрегатор получает неизменяемую базу юнитки, выбранный набор количеств и один реестр расходов. Не зависит от интерфейса, файловой системы и Ozon-клиента. Здесь находится формула раздела 9.
5. **UI.** `EconomicsWorkspace` владеет карточками/целями/периодом; компонент итоговой панели владеет режимом количества, загрузкой, ошибками и финансовым кешем. Он получает ссылку только на собственный DOM-контейнер. Не вводить общий контроллер для всех вкладок.

В публичном результате разделить:

- `pricing_basis_id`, текущий `analysis_snapshot_id` и источник/период весов;
- `mode`, выбранный `period`, источник и полноту количества;
- `profit_before_common`, `advertising_total`, `other_common_total`, `profit_after_common`, модельную выручку и маржу;
- `covered_qty`, непокрытые SKU/события и полноту результата;
- `expenses_source_id`, источник/время загрузки/покрытие расходов;
- `real_drr_rate`, `planned_drr_rate`, `applied_drr_rate`, `applied_drr_source` в карточках.

Результат новой версии API добавить совместимо либо версионировать явно. Не оставлять поле прежней «прибыли по начислениям» с новым смыслом под старым названием. Существующие пути `/api/economics/workspace`, `/api/economics/buyouts/sync`, `/workspace`, `/export` можно сохранить с уточнением контрактов; отдельный внешний сервис не нужен. Количество запросов определяется загрузкой новых данных, а не каждой сменой режима.

Кеш финансовых данных — текущий backend-memory store, привязанный к кабинету и периоду. Итог валидируется по актуальным базе/настройкам/загрузке себестоимости. Смена кабинета исключает прежние финансовые данные даже при прежнем FILES-снимке. Новая БД, месячная история затрат и сохранение API-ключей на frontend не требуются.

### 14.4. Порядок реализации

Один новый PR с одной целью: согласованная юнитка и её итог за период. Технические коммиты внутри него:

1. Зафиксировать тестами нынешние владельцы, источники и неизменяемые Plan/Flow-контракты; отделить панель от внешнего контейнера без изменения формул.
2. Добавить неизменяемые входы/единую базу на штуку, подстановку ДРР и расчёт без продаж; подключить тарифный подбор на цене-кандидате.
3. Нормализовать количества и роли финансовых расходов; ввести чистый агрегатор с одинаковой базой для обоих режимов.
4. Подключить локальную панель, компактные карточки и понятные подписи источников; сохранить состояния ввода/раскрытий.
5. Обновить XLSX, `DESIGN.md`, `UX-CONTRACT.md` и актуальную спецификацию финансового режима. Пометить изменённые положения документа 02.10 как заменённые, не оставлять два противоречащих активных контракта.
6. Выполнить приёмку, независимое ревью и CI на финальном head. PR не мержить и auto-merge не включать.

Создание исполнимого плана с точными сигнатурами/тестами выполняется после ревью этого ТЗ. В этом документе не подразумевается разрешение начать реализацию или менять открытый PR №206.
