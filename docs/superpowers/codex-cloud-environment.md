# Codex Cloud — ограничения среды проекта

Этот документ отделяет неизменные требования продукта от временных свойств
конкретной задачи в Codex Cloud. Такое разделение необходимо, чтобы сбой среды
не превращался незаметно в новое архитектурное решение.

## Что является частью архитектуры проекта

К **PRODUCT CONSTRAINT** относятся согласованные решения проекта:

- TypeScript как язык разработки;
- esbuild как сборщик;
- Vitest как средство тестирования;
- статический offline release, запускаемый через `file://`;
- отсутствие runtime backend, сервера и сетевых зависимостей у release.

Эти решения определены архитектурной спецификацией. Их нельзя менять только
потому, что отдельная Cloud task не получила доступ в интернет.

## Что является свойством Codex Cloud environment

К **EXECUTION ENVIRONMENT CONSTRAINT** относятся условия запуска конкретной
Cloud task:

- доступ к npm registry может быть отключён;
- интернет-доступ задаётся на уровне environment;
- GitHub CLI внутри container может отсутствовать или быть не авторизован;
- публикацию PR может предоставлять внешний/native Codex workflow, а не `gh`.

Эти свойства могут блокировать выполнение или публикацию конкретной задачи, но
не определяют устройство продукта. В частности, отсутствие сети во время
разработки не означает, что следует заменить утверждённые инструменты или
добавить runtime backend.

## Настройка environment для sklad_ozon

По умолчанию Agent Internet Access не является обязательным для разработки
проекта. Codex Cloud должен сначала использовать стандартные механизмы среды:

- automatic setup;
- доступные package facilities;
- cache;
- уже подготовленное окружение.

Включать Agent Internet Access следует только тогда, когда конкретная задача
действительно требует внешний ресурс, который стандартное окружение
предоставить не может. Не следует превращать internet access в постоянное
требование проекта. Offline-режим готового приложения остаётся отдельным
продуктовым требованием.

## Работа с npm-зависимостями

Не следует выполнять прямой network probe через `npm view` только для проверки
исходящего сетевого доступа. Нужно начинать с обычного workflow текущей задачи,
используя стандартную настройку среды.

Если фактически необходимая операция — например, `npm install`, `npm ci`,
сборка или тест — завершается ошибкой из-за невозможности получить зависимость,
это является **environment blocker**. Блокировка определяется фактической
невозможностью выполнить текущий PR, а не результатом отдельной диагностической
проверки сети. В таком случае следует сообщить точную команду и ошибку. Нельзя
менять архитектуру, согласованный stack или создавать самодельные замены
инструментам ради обхода ограничения среды.

## GitHub access

Ошибка `gh auth status` сама по себе не блокирует Codex Cloud task. Не нужно
требовать `gh issue view`, если требования уже зафиксированы в актуальных
документах репозитория. GitHub issues в таком случае являются дополнительным, а
не основным источником требований.

Workflow проекта не должен зависеть от наличия команды с конкретным именем
`make_pr`: для публикации следует использовать доступную в задаче native
возможность Codex Cloud. Если публикация недоступна, нужно сохранить проверенную
незавершённую работу, когда это разрешено средой, и точно описать ограничение —
не удалять результат и не придумывать другую архитектуру. Более строгие
platform/system instructions имеют приоритет.

## Что произошло на первой попытке PR1

- действовавшие repository instructions требовали обязательный `npm view`
  preflight до начала реализации;
- этот preflight получил HTTP 403;
- после сравнения с другими проектами Codex Cloud выяснилось, что прямой Agent
  Internet Access не должен быть обязательной предпосылкой;
- сама ошибка `npm view` не доказывала невозможность выполнить PR1;
- отсутствие авторизации `gh` было дополнительным наблюдением, но не корневым
  техническим блокером;
- после этой попытки изменений в репозитории не осталось.

Правильный подход — начинать обычную реализацию и считать среду заблокированной
только при фактическом сбое необходимой операции установки, сборки или
тестирования из-за недоступности зависимости. Это не гарантирует доступность
любой зависимости без сети; обязательный отдельный network probe был
некорректным gate.

## Правило на будущее

**Environment limitations must not silently become product architecture
decisions.**

При ограничении среды следует зафиксировать точный blocker, сохранить валидную
проверенную работу и повторить задачу в подходящем environment, а не менять
архитектуру продукта.
